### Added

- Build Size: the third area, scan only, every byte download size. Two scopes, the last build and the whole project. From the last build report: the shipped size, native libraries per ABI, managed assemblies, serialized asset data, `Resources` and StreamingAssets weight, and the packed assets and folders ranked when the build was made with `BuildOptions.DetailedBuildReport` (Advice tells how when it was not). Textures Unity stored raw although compression was requested, with the fix that applies (format override, pad the source, lift the Max Size clamp, or re-export), large models with mesh compression off and the error Medium would take, the stripping level and scripting backend, shared libraries missing from an ABI, stray files under an ABI folder, shipped debug symbols, and `Resources` folders that dominate the payload. The scope dropdown now drives the scan.
- Dependencies: the second area. It reads every resolved package from the Package Manager (source, version, whether the manifest names it, what it depends on, its size on disk, and how many of the project's own assembly definitions reference it), the plugins in the third-party folders (assembly definitions, libraries, scripts, and the scripts no definition claims), the assembly names two files claim, and the scripting defines of the active build target. Findings for git packages that follow a tag (Advice) or a branch (Warning) with the commit to pin, packages resolved from a local path, manifest packages no definition references, plugins whose scripts compile into the predefined assemblies, and name collisions. The package map draws packages grouped by source and plugins, with their dependencies. Sizes of registry and git packages are measured once per Editor session.
- Project settings, under Project Settings > Clarity Game Optimizer and stored in `ProjectSettings/ClarityGameOptimizer.asset` for the team to share: the third-party folders (one per line, `Assets/Plugins` by default) whose assemblies count as plugins rather than the project's own code, and the two Architecture thresholds, the hub fan-in and the large-assembly script count. The Architecture scan reads them instead of constants.
- The window, `Window > Clarity Game Optimizer`: a rail of the seven areas with the finding count of each scanned one (the six that cannot scan yet say which release they are planned for), a scope dropdown and Scan, summary cards for the area's headline metrics, the findings most severe first with severity colours and a detail line (double-click a row to show its evidence in the Project window), an Export menu that writes every file to the report folder, opens it, saves any single report or diagram file elsewhere or points the package at an archify checkout, a Render button that scans if needed, writes, renders with archify and opens the HTML, and a status bar. Scan results live for the session only; a recompile starts the window empty. The two `Tools` menu items are gone: the window does what they did.
- Diagrams: the Architecture scan also writes the assembly map as archify JSON (`assemblies.architecture.json`, an `architecture` diagram at the `standard` quality profile: the project's own assemblies first, a quarter of the twelve slots for the packages and plugins they use most, one component per row so nothing routes through a node, group as a tag, line weight for folded references, a card with the findings above Info), as Graphviz DOT and as Mermaid (the whole graph, grouped), and renders the HTML with archify when it is found through the window's Locate archify, `ARCHIFY_HOME` or an agent skill folder and Node.js is on the path. A `Diagrams` workflow validates the committed fixtures with the pinned archify release on every pull request.
- Graph layout and curation in Core, the step between a report and a diagram: `LayeredLayout` places nodes on a grid so dependencies read left to right (column = longest path from a node nothing depends on; rows keep a group together, heaviest first; cycle-closing edges are dropped deterministically and counted), and `GraphCuration` keeps the heaviest twelve nodes, folds the rest into one "Other" node per group, merges the edges that follow with a count, and offers one view per group, five at most.
- Architecture: the first area. It reads every script assembly from the compilation pipeline and writes `report.json` and `report.md` under `ClarityGameOptimizerReports/architecture/` beside `Assets`. One node per assembly typed as Runtime, Editor, Test (read from the `.asmdef`) or External (under `Packages/` or `Assets/Plugins/`) and grouped by that role, one edge per reference with fan-in as the weight, metrics for assemblies, scripts, references and the share of scripts outside any assembly definition, and findings for that share (graded by its size), for hubs referenced by five or more assemblies, and for assemblies of 250 scripts or more.
- Report model: one `Report` shape for every area (`ClarityGameOptimizer.Core`): metrics, findings with a severity, a budget, measured and projected values, a verdict, a fix id and evidence paths, a graph of nodes and edges, and notes. A validator enforces the invariants, and two exporters write `report.json` (format `clarity-game-optimizer/report`, version 1, documented in `Documentation~/report-format.md`) and `report.md`, which keeps download size and runtime RAM in separate tables.
- Package scaffold: `package.json`, the seven assembly definitions, `IdentifierSlug` in `ClarityGameOptimizer.Core` with EditMode tests, the `DevProject~` development project, the CI test matrix, the tag-driven release workflow, the README and six decision records.
- Repository workflow: contribution guide, `AGENTS.md` rules for AI assistants, local git hooks, pull request and issue templates, Conventional Commit title check, Dependabot for GitHub Actions.
